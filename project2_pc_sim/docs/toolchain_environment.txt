### 3. RF internal runtime shape

The retained RF chain is orchestrated by the Qt process:

1. Qt starts `python\wav_to_pulses.py`
2. Qt writes `%TEMP%\project2_pc_sim_runtime\pulse_runtime.txt`
3. Qt writes `%TEMP%\project2_pc_sim_runtime\pulse_runtime.json`
4. Qt preloads `pulse_runtime.json` and builds an in-memory `candidate_idx/idx -> candidate_wav_sec/wav_sec` lookup before starting replay
5. Qt starts `rf_gateway.exe --rf-input - --stable-repeat 1 --min-publish-confidence 0.92`
6. Qt starts `python\replay_pulse_timeline.py`
7. replay sends timed AA55 frames to `rf_gateway` through stdin; it does not emit `FRAME_TS` or `FRAME_META`
8. `rf_gateway` emits one decoded event per stdout line as JSON including `addr`, `key`, `conf`, `src`, `pulses`, and `seq`
9. Qt parses those gateway stdout JSON lines, backfills `wav_sec` from the preloaded `seq -> wav_sec` map when needed, then updates the RF page and local logs

The current Qt-side Stage-1 preprocessing invocation is:

```text
python\wav_to_pulses.py --wav <wavPath> --max-frames 0 --out-txt <pulse_runtime.txt> --out-json <pulse_runtime.json>
```

The current Qt-side replay invocation is:

```text
python\replay_pulse_timeline.py --pulse-json <pulse_runtime.json> --speed <wav_speed> [--loop]
```

The current gateway invocation is:

```text
rf_gateway.exe --rf-input - --stable-repeat 1 --min-publish-confidence 0.92
```

The current RF metadata path visible to Qt is:

- gateway stdout JSON fields `addr`, `key`, `conf`, `src`, `seq`
- Qt-backfilled candidate replay time / `wav_sec`

There is no `FRAME_TS` / `FRAME_META` sideband path in the current replay chain.

The RF replay report written by Qt is a local dashboard log generated after parsing the JSON event. It is not a real MQTT publish.

This `wav_sec` metadata is retained RF replay metadata. It is not standalone profiling residue.
