RKNN C Acceleration Design Notes (from referenced article)
Date: 2026-04-12

1) Core idea
- The key value is not "single inference gets faster".
- The key value is "higher throughput with ordered output in real-time stream".

2) Why simple multi-thread is not enough
- Worker completion is naturally out of order.
- Pure sorting or fixed batch wait adds CPU overhead or fixed latency.
- Real-time chain needs bounded queue + ordered commit, not only more threads.

3) Recommended pattern
- Assign sequence id `seq` per input frame.
- Push frames into bounded input queue.
- Multiple workers infer asynchronously.
- Workers write result into bounded result buffer.
- Maintain `next_commit_seq`.
- Only commit output when `next_commit_seq` result is ready.
- If frame 3 finishes before frame 1/2, keep it buffered until 1/2 arrive.

4) Data structure guidance
- Use fixed-size ring buffer for result slots.
- Each slot stores:
  - payload
  - real sequence id
  - ready flag
- Commit loop advances strictly in sequence order.

5) Fit to current project
- Current PC sim already proves functional correctness.
- Main remaining issue is low throughput.
- Migration to C-side pipeline can target:
  - decode/preprocess split
  - RKNN worker pool
  - ordered commit stage
  - transport send stage

6) Pros/cons for this project
Pros:
- Better throughput without output disorder.
- Better control of queue growth and latency spikes.
- Cleaner scaling path for RK3568 deployment.

Cons:
- Higher implementation complexity.
- Requires strict lifecycle/ownership around buffers.
- Needs careful profiling to avoid moving bottleneck to preprocess/postprocess.

7) Implementation checklist for next phase
- Define frame struct with `seq`, timestamps, and payload refs.
- Implement bounded lock-free or mutex queue for input.
- Build worker pool and result ring.
- Add ordered commit logic.
- Keep per-stage timing metrics in one profile schema.
- Validate with same-run RF+Vision acceptance set before replacing current path.
